# Mobile Test Bench

A JetBrains IDE plugin that mirrors Android emulators, Android devices and iOS simulators in a tool window, lets you control them with mouse and keyboard, and includes an element inspector with ready-to-copy **Mobilewright** and **Appium** locators.

The plugin only depends on `com.intellij.modules.platform`, so it runs in IntelliJ IDEA, WebStorm, PyCharm, Android Studio and the other IntelliJ based IDEs (2025.3 and newer).

## Requirements

**[mobilecli](https://github.com/mobile-next/mobilecli) is required for most of the plugin.** Install it with `npm install -g mobilecli` (or Homebrew); the plugin finds it on the IDE's `PATH`, then in `/opt/homebrew/bin` and `/usr/local/bin`. Without it:

* **Android 17 has no element inspector.** `uiautomator dump` is killed by the system (exit 137), and mobilecli is the only other source. Mirroring and input still work through adb.
* **Physical iPhones are not listed**, and iOS simulators lose input and the inspector unless WebDriverAgent is running.
* **Android phones mirror at about 1 frame per second** (adb screenshots instead of the mobilecli stream).
* These features need mobilecli and do not work without it: Location, Crashes, WebView, the Input tab's clipboard, screen recording, Device Power and Orientation.

Also needed: **adb** (Android SDK platform-tools) for Android devices and **Xcode** (`xcrun simctl`) for iOS simulators, only for the platform you use. Physical iPhones also need mobilecli's on-device agent, installed once with a development provisioning profile (see *iOS device* below).

## Features (MVP)

| | Android emulator | Android device | iOS simulator | iOS device |
|---|---|---|---|---|
| Screen | Live stream via emulator gRPC (`streamScreenshot`) | `mobilecli screencapture` MJPEG (fallback `adb exec-out screencap` polling, about 1 frame per second) | `mobilecli screencapture` MJPEG (or WDA MJPEG without mobilecli), fallback screenshots | `mobilecli screencapture` MJPEG, fallback `mobilecli screenshot` |
| Input | gRPC `sendMouse` / `sendKey` | `adb shell input` | `mobilecli io` (or WebDriverAgent without mobilecli) | `mobilecli io` (tap, swipe, text, button, keys) |
| Hierarchy | `mobilecli dump ui` (fallback `uiautomator dump`) | `mobilecli dump ui` (fallback `uiautomator dump`) | `mobilecli dump ui` (or WDA `/source` without mobilecli) | `mobilecli dump ui` |

* **Mouse:** click = tap, drag = swipe, scroll wheel = vertical swipe.
* **Gestures:** hold the mouse still for about 700 ms (setting **Long press time**, 300 to 3000 ms) for a **long press** (a ring shows when it fires, and the release sends nothing more); **double click** = double tap; **Option/Alt + drag** = press, hold 700 ms, then drag. Inspect mode keeps its meaning (a click selects), but Option/Alt gestures still go to the device.
  * Long press works everywhere: Android via emulator gRPC or `adb shell input swipe x y x y ms`, iOS via `mobilecli io longpress` (or a WebDriverAgent pointer action on a simulator without mobilecli). Verified on the Pixel_9 emulator and the iPhone 17 Pro simulator with mobilecli, 700 ms.
  * Double tap and drag with hold need the **Android emulator gRPC** connection: adb and mobilecli calls take 150 ms or more each, past Android's 300 ms double tap timeout, and mobilecli has no double tap or gesture command. Where they are unavailable (adb only, iOS through mobilecli) a double click stays a plain tap and Option/Alt + drag stays a normal swipe. The double click always sends its first click as a tap straight away (no delay on every tap), so the app sees a tap followed by the double tap.
  * Recording: `await loc.longPress({ duration: 700 });` and `await loc.doubleTap();` on the same locator a tap would get (the tap before a double click is folded into the double tap). Mobilewright has no drag API, so a drag with hold is recorded as a comment and not replayed. Replay performs long presses and double taps.
  * Not verified: the plugin's own gRPC code (only a scratch harness with the same calls was run), iOS simulator through WebDriverAgent (WDA was not running), and the iOS hold-drag and true iOS double tap (no working mobilecli path was found; the WDA payloads are only unit tested).
* **Keyboard:** type while the screen has focus. Enter, Backspace and (Android) Escape = Back.
* **Toolbar:** Refresh Devices, Connect, Disconnect and Device Power; Back, Home, Recent Apps, Type Text and the Landscape toggle; Inspect Elements, Refresh Hierarchy, Freeze, Grid, Record and Device Tools; Generate Page Object, Screenshot, Record Screen to Video and Settings. Each button has a tooltip.
* Hover the status line to see the transport and, after a fallback, the reason (emulator gRPC failed or is unavailable, mobilecli or WDA MJPEG stream ended, WebDriverAgent not configured). The wording was not checked against live fallbacks.
* **Record Screen to Video** (toolbar toggle, needs mobilecli): choose where to save an MP4, record, and press the button again to stop; the status line shows the saved file and its size. Disconnecting also stops and saves it. Setting **Screen recording | Time limit (seconds)** (Settings | Tools | Mobile Test Bench, 0 = no limit, up to 3600) stops and saves it by itself; the limit is read when the recording starts. The automatic stop was not tried against a real device. Emulator and simulator frames only change when the screen changes, so a still screen gives a very short video.
* **Device Tools** (the console icon) opens a tabbed panel below the screen with the tabs Log, Apps, Open URL, Crashes, Location, Display, Input, Network, Battery, Biometrics, WebView, Files, Performance, Visual and Notifications, described below. The first tab, **Log**, is a live log: `adb logcat` for Android emulators and devices, and the simulator's log stream for iOS simulators (a physical iPhone uses `mobilecli device logs`, experimental). Filter by **Level** (Info and up by default), by text in the message, by tag or process, and by **App**: for Android type the package name (`com.example.app`; the app's process ids are looked up and followed when it restarts), for iOS part of the process name. Errors and warnings are coloured, multi-line messages (stack traces) stay together, **Pause** freezes the list while the log keeps arriving, **Clear** empties it, **Save...** writes the lines that are shown to a file, and right-click copies the selected lines. The newest 20,000 lines are kept. The **.*** toggle makes the message and tag filters regular expressions (case-insensitive, found anywhere in the text; the App field stays plain text); an invalid pattern turns its field red, the tooltip and the status line give the reason, and it is ignored until fixed. Regular expressions only look at the first 20,000 characters of a message, but a pathological pattern can still be slow. The text of the message filter is highlighted inside the rows (first line of each message). **Open in Editor** (right-click, or double-click a row) opens the source of a stack trace line such as `at com.example.Foo.bar(Foo.java:12)` or `(Foo.kt:34)`: it looks the file name up in the project (platform file index, so only files in the project, not libraries or Android framework classes), prefers the folder that matches the package when several files share the name, and opens it at that line; a message with several lines uses its first frame, and the status line says when nothing was found. `(Native Method)`, `(Unknown Source)` and obfuscated frames are rejected. **Restart app** (next to the App field, enabled when the App field is filled) un-pauses, empties the list, terminates and relaunches the app named in the App field with `mobilecli apps terminate/launch` (a package on Android, a bundle id on iOS; a failing terminate is ignored, a failing launch is shown) so the first lines of the start are captured; on Android the new process id is looked up for up to 5 seconds so those lines are shown. On iOS a bundle id in the App field also matches the process name by its last part (`com.example.MyApp` matches `MyApp`). A physical iPhone uses `mobilecli device logs` as an experimental source (status line says so); the other devices keep adb and simctl. mobilecli was evaluated as a source for emulators and simulators and not used there: its Android stream has no history (`-T 1`), its iOS stream has no Debug lines, its `--filter` is exact case-sensitive equality that hangs silently when nothing matches (so none of our filters is passed to it) and it adds nothing our parsers do not already give. Closing a log now ends the whole process tree (the mobilecli wrapper leaves its native child behind otherwise). Not verified: a physical iPhone (no device here), the mobilecli daemon being down, Restart app on an iOS simulator (only Android was run), Swift/Objective-C frames (only Java/Kotlin format was checked against real logcat), and opening the file in the IDE by hand (the lookup is tested with fixture files, the open itself uses `OpenFileDescriptor`). The iOS log is very busy (about 100 lines per second), so the filters matter there.
* The **Apps** tab of Device Tools lists the installed apps (name, id, version) with a filter box, a **Hide system apps** checkbox (on by default, remembered) and **Refresh**. mobilecli does not flag system apps, so on Android an app counts as system when it is not in `adb shell pm list packages -3` (third-party apps), and on iOS when its bundle id starts with `com.apple.` (Apple apps installed from the App Store, such as Pages, are hidden too). The selected app stays visible; if the Android package list cannot be read nothing is hidden and the status line says so, otherwise it shows how many system apps are hidden. Not verified on a device: the split was only unit tested, not run against a real emulator, simulator or phone. The foreground app is shown above the list (with the activity on Android, "Home screen" on iOS) and in bold in the list. Buttons and the right-click menu: **Launch** (starts at once, also on double-click), **Launch with options...** (asks for an optional locale such as `fr-FR,en-GB`, and on Android an optional activity), **Terminate**, **Clear data** and **Uninstall** (both ask for confirmation; clearing is Android and simulator only), **Copy id**, **Show log of this app** (fills the Log tab App filter and switches to it) and **Install...** (.apk for Android, zipped .app (.zip) for a simulator, .ipa for a real iPhone). You can also drop such a file on the tab. Needs mobilecli. The Android list contains launchable apps only; iOS lists system helper apps too, so use the filter. **Reset state...** (button and right-click menu) opens a dialog with four ticked checkboxes: Terminate the app, Clear its data, Reset its permissions (Android: revoke all runtime permissions and clear their flags; simulator: `simctl privacy reset all`) and Relaunch it afterwards. The steps run in that order, each row shows its result and time as it goes, and the first failure stops the run and shows the exact error. Clear and permissions are skipped with a note on a real iPhone. The choices are remembered. Note that on Android and on the simulator Clear data already kills the app, and on Android it also revokes runtime permissions, so the permission step matters mainly when Clear is unticked. Android terminate succeeds even for a package that does not exist. Checked by hand against mobilecli on the emulator and simulator: terminate, clear, permission reset and launch separately (about 1 s on iOS, about 13 s on Android with 3 runtime permissions). Not verified: the dialog itself end to end, a real iPhone, whether `simctl privacy reset` terminates the app when a real entry changes, apps with many runtime permissions, and that the app is in front after the relaunch on Android (it only reports that mobilecli accepted the launch). Verified on the Android emulator and iOS simulator for list, foreground, launch and terminate. Not verified: install, uninstall, clear data, the effect of `--locale` on Android, and real iPhones. The result of an action (including an error such as a failed install or a wrong activity name) stays in the status line below the list while the list reloads.
* The **Open URL** tab of Device Tools opens a URL or deep link on the device (`https://...`, `myapp://...`, also `tel:`, `geo:`, `market://`). Type or pick a link and press **Open** or Enter; picking from the history only fills the field. The history keeps the last 20 distinct links that opened successfully, newest first, and is remembered across sessions (**Clear history** empties it). The value must be one line, contain no spaces and start with a scheme. The status line shows the result or the device's error in plain words (iOS only reports an exit code, so 115 is shown as "No app on the device handles this URL scheme" and 206 as "Not a valid URL"). Success only means the system accepted the link, not that the app showed what you expected. Needs mobilecli. Verified on the Android emulator and iOS simulator with https, tel, geo, market, maps and unresolvable schemes. Not verified: a custom scheme handled by a real app of your own, real devices, very long or non-ASCII URLs, and whether iOS shows an "Open in app?" prompt for some schemes. Android Settings cannot be opened this way (it needs an intent action, not a URI).
* The **Crashes** tab of Device Tools lists the crash reports of the connected device (time, process or app, id), newest first, with a filter box and **Refresh** (it loads when the tab is shown; there is no polling). Select one to read the full report in a read-only monospace area, with **Copy** and **Save...** (`.txt` for Android, `.ips` for iOS). A bold red line above the report shows the crash summary when it can be found: the exception for Java crashes (`java.lang.IllegalStateException: ...`), the signal and fault address for native Android crashes (`SIGSEGV (SEGV_MAPERR) fault addr 0x...`), and exception type, signal and termination reason for iOS (`EXC_CRASH (SIGABRT) - Abort trap: 6`). Needs mobilecli. Verified on the Android emulator and iOS simulator for list and get (real output is in the test fixtures). Caveats: on iOS mobilecli reads the Mac's `~/Library/Logs/DiagnosticReports`, so the list holds host crashes (macOS apps too), not only the simulator's; the tab says so. The Android list comes from the logcat crash buffer, so it includes system processes, ANRs are not listed, and the process name of a Java crash is often a framework class such as `android.os.Parcel`, not the app. Not verified: an empty list, a crash of a simulated iOS app, physical devices.
* The **Location** tab of Device Tools overrides the device GPS location with one point (needs mobilecli). Enter latitude and longitude (-90..90, -180..180, dot decimals, rounded to 6 decimals when applied; pasting `52.37, 4.90` into either field fills both) or pick a place: Amsterdam, London, New York, Tokyo, Sydney, or places you saved with **Save place...** (name plus the current coordinates, remembered in the plugin settings; **Delete place** removes a saved one, presets stay). **Set location** applies it and the status line shows the result or mobilecli's own error text; **Clear override** removes it and is always available. The override is held by the mobilecli background process, so it may not outlive that process, and an app only sees it when it has location permission. Verified on an iOS simulator (set, error and clear via mobilecli); not verified: that an Android app receives the coordinates, whether the override survives the daemon's idle exit, and physical devices. Route simulation is not implemented.
* **Permissions...** (button and context menu of the **Apps** tab, one app selected) opens a dialog for that app. On **Android** it lists the app's runtime permissions as read from `adb shell dumpsys package` with their state (Granted / Denied) and flags; **Grant** and **Revoke** change the selected one (`pm grant` / `pm revoke`) and the list is re-read afterwards, so the table shows the real state (pm silently ignores a permission the app did not request, which is why only the app's own permissions are offered). Install-time permissions such as INTERNET are counted but cannot be changed. **Reset all** is not the system reset (Android has no per-app one; `pm reset-permissions` would hit every app and is never used): it revokes every runtime permission and clears its user-set and user-fixed flags so the app can prompt again. On an **iOS simulator** it offers the `simctl privacy` services (all, calendar, contacts, contacts-limited, location, location-always, photos, photos-add, media-library, microphone, camera, motion, reminders, siri) with Grant / Revoke / Reset; the state is shown as Unknown because it cannot be read, and simctl grant and revoke may terminate the app if it is running (reset did not in the scout test). Camera works but is not in simctl's help text; notifications are not a simctl service. Reset always passes the app's bundle id. Physical iPhones are not supported. A log under the table shows each command and its result or first error line. Verified by scouting on the Android 17 emulator (dumpsys layout, grant and revoke of a denied permission, error output) and on an iOS 26 simulator (grant, revoke, reset of several services); the dialog itself and the following are not verified: revoking a granted permission (kills the app), the Reset all sequence end to end, POST_NOTIFICATIONS, Android below 17, work profiles, and the iOS services location-always, photos-add, media-library, reminders, contacts and all.
* The **Display** tab of Device Tools changes how the device looks, to test dark mode, large text and flaky-animation problems. Each control reads the device when the tab is shown (**Refresh** reads again), applies at once, and the status text next to it shows what the device reports afterwards or the tool's own error text. **Dark mode**: Auto, Light or Dark on Android (`adb shell cmd uimode night auto|no|yes`; a schedule mode such as `custom_schedule` shows as no selection), Light or Dark on an iOS simulator (`xcrun simctl ui appearance`). **Font size**: Small, Default, Large, Largest; on Android these write `font_scale` 0.85, 1.0, 1.15 and 1.3, on iOS the content size categories small, large, extra-extra-large and accessibility-extra-extra-extra-large (any other value on the device shows as a custom value). **Disable animations** (Android only) sets the window, transition and animator scales to 0; unchecking deletes the three settings. **Show touches** and **Layout bounds** (Android only) set `show_touches` and `debug.layout`. **Pointer location** and **Don't keep activities** (Android only) set `settings put system pointer_location` and `settings put global always_finish_activities` (1/0; unchecking writes 0, Reset deletes them; not verified on a live device, iOS shows "Android only"). **Reset to defaults** restores exactly what this tab changed on that device (values it remembered the first time it changed them, including "unset"); if this tab changed nothing yet it applies the platform defaults (Android: auto, 1.0, animation settings deleted, touches, layout bounds, pointer location and don't keep activities off; iOS: light, large). The remembered values live only in the IDE session, and settings stay on the device after the tab or IDE closes. Physical iPhones show "not supported". It uses adb and `simctl` directly, not `mobilecli device settings apply`, because that cannot read the state, does nothing on iOS animations and fails for iOS appearance. Verified on a Pixel 9 emulator (Android 17) and an iPhone 17 Pro simulator (iOS 26.5) with the commands above, and the layout bounds redraw of a running app. Not verified: the Show touches dots on screen (only the setting round-trips), the panel UI itself against live devices, physical Android devices (`debug.layout` and `settings put` may be refused), other Android or iOS versions, and iOS animations (there is no control; `ReduceMotionEnabled` writes but its live effect is unproven). **Language** and **Time zone** (the same tab, each with an editable combo and an Apply button; both show the device value when the tab is shown). Language presets: en-US, nl-NL, de-DE, fr-FR, es-ES, ja-JP and ar-SA (right-to-left); you can also type any BCP 47 tag (shape checked, the device may still not know it). Time zone presets: Europe/Amsterdam, UTC, America/New_York, Asia/Tokyo, Australia/Sydney, or type an IANA id (checked against the JDK's list). Android (checked on Android 17 / API 37): language runs `cmd locale set-device-locale <tag>` (live, no restart, running apps recreate their screens), read back with `get-device-locale`; the list is read from `settings get system system_locales`. WARNING: `set-device-locale` replaces the WHOLE language list with one tag, so a confirm dialog appears whenever the device list has two or more languages (decided from the live list, not from earlier changes), and Reset to defaults can only bring back the first one; re-add the others in Settings > System > Languages. Time zone runs `cmd alarm set-timezone <id>` (live, persists), read back with `getprop persist.sys.timezone`; if Automatic time zone is on in Settings the network may switch it back later. Both commands exit 0 for bad input, so the output text is checked and the value is read back; a mismatch is shown as an error. iOS simulator: language writes `AppleLanguages` (the new tag first, your other languages kept) and `AppleLocale` through `simctl spawn defaults write -g`; it takes effect for apps the next time they start (relaunch the app), while the Home screen/SpringBoard keeps the old language until the simulator or SpringBoard restarts (not done automatically). The iOS time zone follows the Mac, so the combo is disabled and the Mac's zone is shown. A write that fails without changing the device leaves no Reset baseline behind. Locale writes, Reset and Refresh do not overlap: Reset and Refresh wait (Reset is disabled) while a language or time zone write runs, and Reset restores the locale part even when the other Display values could not be read. Reset to defaults also restores what these controls changed: the Android time zone and first language, the iOS language list and locale exactly as read (keys that did not exist are deleted). For one app only, use Apps > Launch with options... > locale (nothing else changes). Verified by the scout on the Pixel 9 emulator (Android 17) and the iPhone 17 Pro simulator (iOS 26.5): the commands, read-backs and the iOS restore. Not verified: the new panel controls on live devices; Android older than 17 (`cmd locale set-device-locale` may not exist, the panel then shows the tool's error); that ar-SA flips the layout to right-to-left; whether `-u-` region extensions survive a change and restore; whether automatic time zone reverts a manual zone after a longer time; iOS 27 runtimes, the SpringBoard restart, and physical devices. Not implemented: Android per-app language button, restoring a multi-language Android list.
* The **Input** tab of Device Tools has three groups; a status line at the bottom shows the exact result or the tool's own error text. **Hardware buttons**: Volume up, Volume down, Home, Power / Lock, Back, App switch, Assistant (Android) and Shake (iOS simulator), each enabled only on the platform where it was found to work (the others are disabled with a tooltip). On Android they go through `mobilecli io button` (names must be UPPER CASE; adb `input keyevent` is used when mobilecli is missing, and always for Assistant, key 219). On iOS simulators they go through mobilecli too (HOME, VOLUME_UP, VOLUME_DOWN, LOCK; there is no Power or Siri), and Shake sends `xcrun simctl spawn <udid> notifyutil -p com.apple.UIKit.SimulatorShake` (an app has to react to it, for example "Undo Typing" in a focused text field, whose alert stays until dismissed). Power / Lock **toggles**: a second press wakes the screen; **Wake** (Android) sends the WAKEUP key. Because "ok" does not prove an effect, a button press is followed by a read-back: on Android the screen state (`dumpsys power`) and the media volume (`cmd media_session volume`), on iOS the lock state (`notifyutil -g com.apple.springboard.lockstate`). The first volume press while the volume panel is hidden may only show the panel without changing the level. After Lock on iOS, wake it and press Home to unlock, sometimes twice. **Keyboard**: Tab, Esc, Enter, Backspace, Delete and the arrow keys are sent with `mobilecli io keys` (Android falls back to adb key events without mobilecli; iOS needs mobilecli). **Hide keyboard** (Android only) reads `mImeWindowVis` and sends Escape when the keyboard is shown; it never sends Back, which would leave the screen. There is no Show keyboard (tap a text field) and no way to hide the iOS keyboard with these tools. **Clipboard** (needs mobilecli): a text area with **Get from device**, **Set on device**, **Set and paste** (sets, then presses ctrl+v on Android or cmd+v on iOS) and **Clear**. Adb cannot read or set the Android 17 clipboard and `simctl pbcopy` did not work on the tested simulator, so without mobilecli the group is disabled and says so. **Android emulator clipboards are shared with your computer**: Set on device and Clear also change your Mac clipboard. On iOS, paste shows an "Allow Paste" prompt on the device that you must answer; the plugin cannot confirm the paste. Verified with the commands above on a Pixel 9 emulator (Android 17) and an iPhone 17 Pro simulator (iOS 26.5), mobilecli 1.0.17. Not verified: the panel UI against live devices, physical devices, Assistant on a device without the Google app, wake on a device with a PIN lock, a full soft keyboard (the tested AVD shows only Gboard's hardware-keyboard toolbar) and Escape hiding it, iOS volume effects, very long clipboard text, non-text clipboard content on iOS, and clipboard text that starts with `-` (sent after `--`).
* The **Network** tab of Device Tools changes the network of an Android device. **Airplane mode**, **Wi-Fi** and **Mobile data** are read when the tab is shown (**Refresh** reads again) and apply at once (`cmd connectivity airplane-mode enable|disable`, `svc wifi enable|disable`, `svc data enable|disable`); after each change the device is read back every second until it shows the new value (up to 15 s for airplane mode, which takes about 8 s to reconnect when switched off), with a "Reconnecting..." note, and the status text shows what the device reports or the exact error. A "Connection" line says whether Android has a default network (`dumpsys connectivity`, not a ping). Note that Wi-Fi off alone or mobile data off alone leaves the device online, because the other one takes over; only airplane mode, or both off, goes offline. On an **emulator** (serial `emulator-NNNN`) two more controls set **Emulator speed** (full, 5g, evdo, lte, hsdpa, umts, edge, gprs, hscsd, gsm) and **Emulator latency** (none, gprs, edge, umts) through the emulator console (`adb emu network speed|delay`; adb handles the console authentication, the plugin reads no token). The adb exit code is always 0 for the console, so the plugin looks for a `KO:` line in the output. The shown value always comes from `emu network status` (a value that matches no preset shows as custom; full and 5g, and gprs and umts, report the same numbers on the tested emulator). **Reset to normal** restores what this tab changed (the values it remembered before its first change, only those that differ); if the tab changed nothing yet it applies normal: airplane off, Wi-Fi and data on, full speed, no delay. The remembered values are stored only after the first write succeeded (a refused write leaves nothing to reset) and live only in the IDE session, and conditions stay on the device (the emulator stays throttled) after the tab or IDE closes, so the tab shows a note while the emulator is throttled. **iOS simulators** share the Mac network: the tab says so and points to the Network Link Conditioner on the Mac (all Mac traffic) or a proxy; `simctl status_bar` only changes the icons and is not used. Verified with the commands above on a Pixel 9 emulator (Android 17). Not verified: whether the speed and latency profiles really slow the traffic of an app (only the console readback was checked; ping on the emulator gives unusable timings), the panel UI against live devices, physical Android devices (`svc` may be refused), Android below 11 (airplane mode falls back to read only through `settings get global airplane_mode_on`, writes show the error), several emulators at once, and Network Link Conditioner (not installed on the test machine).
* The **Battery** tab of Device Tools simulates the battery of an Android emulator or device with `adb shell dumpsys battery set level|status|ac|usb <value>` and `dumpsys battery reset`. A level slider (0 to 100, applied on release), a status combo (unknown, charging, discharging, not charging, full) and AC / USB power checkboxes apply at once; the device is read back from `dumpsys battery` afterwards and the controls show what it reports, or the error text (dumpsys exits 0 for bad input, so the output text is checked). **Reset to real battery** runs `dumpsys battery reset`. The simulated state stays on the device after the tab or IDE closes, so the tab shows a note while it is active. iOS simulators: the tab explains that `simctl` cannot change the battery (`status_bar --batteryLevel` only changes the icon). Parsing and command building are unit tested; not verified against a live device: the panel UI, whether apps react (low battery, power saver), physical Android devices and wireless charging. The same tab has a **Memory warning** section: pick the foreground app or type a package, choose a level (hidden, running moderate/low/critical, background, moderate, complete) and **Send memory warning** runs `adb shell am send-trim-memory <package> <LEVEL>` so the app's `onTrimMemory` fires (the app must be running; the output text is checked because it exits 0 for an unknown process). iOS simulators: the tab points to Simulator > Debug > Simulate Memory Warning, as `simctl` has no such command. Command building and result interpretation are unit tested; not verified against a live device. Low storage simulation is not implemented.
* The **Biometrics** tab of Device Tools simulates Face ID, Touch ID and fingerprint sensors. **iOS simulator**: **Enroll** and **Unenroll** run `xcrun simctl spawn <udid> notifyutil -s com.apple.BiometricKit.enrollmentChanged 1|0` followed by `-p` of the same name (two processes); **Matching face** and **Non-matching face** post `com.apple.BiometricKit_Sim.pearl.match` / `.nomatch`. On Touch ID models the buttons read finger and post `com.apple.BiometricKit_Sim.fingerTouch.match` / `.nomatch`. Face ID or Touch ID is guessed from the model name (iPhone SE, iPhone 8 and older, iPads other than the Face ID Pros count as Touch ID; Face ID iPads are the iPad Pros except 9.7-inch, 10.5-inch and 12.9-inch 1st/2nd generation), because simctl does not report it. The state line is read with `notifyutil -g` and only shows what this tab or an earlier notifyutil call set, not enrolment done in Simulator.app. **Android emulator** (serial `emulator-NNNN`): a finger preset or id (1 to 10) plus **Touch sensor** (`adb emu finger touch <id>`) and **Lift finger** (`adb emu finger remove`); the enrolled count and accept / reject counters come from `dumpsys fingerprint` (Refresh reads again). Use an id that is not enrolled (preset "Unknown finger 99") to fail. adb exits 0 for the console, so the reply line (OK or `KO: reason`) is parsed; each action shows the exact result. Physical devices and iOS physical iPhones are disabled with an explanation. **What the plugin cannot do**: it cannot enrol a fingerprint on Android (there is no shell command; set a screen lock in Settings > Security, then Settings > Security > Fingerprint, and press Touch sensor for each scan step), and the console replies OK even when nothing is enrolled, so OK does not mean authentication succeeded. For the same reason notifyutil exits 0 for any name: "Posted" only means the notification was sent. Verified on a Pixel 9 emulator (Android 17) and an iPhone 17 Pro simulator (iOS 26.5): the enrol / unenrol effect (in the simulator log, Face ID went from not enrolled to usable and back), the console replies and the `dumpsys fingerprint` output with nothing enrolled. Not verified: the effect of match / non-match with a live LocalAuthentication prompt, Touch ID models and the fingerTouch notifications, an enrolled Android fingerprint and what the counters then show, and the panel UI against live devices.
* The **WebView** tab of Device Tools inspects the web views of hybrid apps and in-app browsers (needs mobilecli; Android and iOS). **Refresh** lists the web views of the **foreground app** (title, URL, app) and loads the DOM of the first visible one; pick another in the combo box. The DOM is shown as a tree (`tag#id.class "text"`; head, script and style nodes are hidden unless you tick the box). Large pages are cut at 2000 elements and the status line says "showing the first 2000 of N elements" (a loaded DOM of a 14,000 element page takes about a second). Selecting a node shows:
  * a **CSS selector** and an **XPath**, each with the number of matches the page itself reports (`querySelectorAll(...).length` and `document.evaluate(...)`; green for 1, orange for several, red for none or an invalid selector) and a **Copy** button. They are generated from the loaded DOM and prefer a unique id, then a test attribute (`data-testid`, `name`, `aria-label`, ...), then tag and classes, then a short child path from the nearest ancestor with a unique id (`#loginForm > button`, `//*[@id='loginForm']/button`). Elements inside `<svg>` or `<math>` use `*[local-name()='path']` steps in the XPath, because plain tag names do not match their namespace. Before the page answers, the count in the loaded DOM is shown.
  * the **attributes** of the element and its own text.
  * a **highlight on the mirror** (orange) of the element: its current bounding rect is mapped to device coordinates with the web view bounds and the page width (x = bounds.x + cssX * bounds.width / pageWidth). The same formula was checked against a real screenshot crop on the Android emulator and against the native UI dump on the iOS simulator. The highlight is a snapshot taken at selection time: it does not follow scrolling (select the node again) and is removed when you leave the tab or change device. An element outside the visible part of the web view (scrolled away, or below the fold) is clipped to the visible part, or not highlighted at all (the note says so).
  * a **JavaScript console**: type script, press **Run** or Ctrl/Cmd+Enter. It runs as an indirect `eval` in the page, so statements, `var`/`let`, comments and `throw` work and the value of the last expression is returned; promises are awaited. The result is shown as JSON, or the error text. mobilecli converts results to JSON: DOM elements come back as `{}` on Android and as an error on iOS, `undefined` and `null` both show as "undefined (or null)", and object keys come back sorted; return primitives or `JSON.stringify(value)`. The console runs in the live page and can change the app.
  * **Native and web:** the inspector keeps showing the native tree. The tab names the native element that owns the web view by comparing bounds (on Android typically `android.webkit.WebView at 0,289 1080x2135`); on iOS the native tree exposes the page as ordinary accessibility nodes, so only the web view bounds are shown (a native node is named only when its type says WebView).
  * **Debug builds only.** mobilecli injects an agent into the app: Android needs a debuggable app, iOS the `get-task-allow` entitlement (a simulator or development build). For other apps the status line shows mobilecli's error with that hint. Browsers (Safari, Chrome) and apps without a web view give an empty list. Web view ids change when a screen is left and re-entered; the tab then lists again (once per action, so a persistent error does not loop) and re-selects by URL and title.
  * Verified on the playground app's Web View screen with real mobilecli 1.0.17 output on an Android emulator and an iOS simulator (list, eval, tree script, rect mapping; the output is in the test fixtures). **Not verified:** the finished tab in a running IDE, XPath counting and the highlight on a device (the commands were exercised only through scripts, the XPath code path not at all), a scrolled or zoomed page (rects are viewport relative), iframes and shadow DOM (not descended into), several web views at once, and real devices.
* The **Notifications** tab of Device Tools sends test notifications; the last line shows the exact output or error of the tool (tooltip: the full text) and a **History** combo reloads any of the last 15 sends (kept in the plugin settings, newest first, no duplicates). **iOS simulator**: pick the app (an editable combo of the installed bundle ids, the foreground app preselected; a bundle id that is not installed gets a warning, because `simctl push` accepts any id), then fill Title, Subtitle, Body, Badge, Sound, Category and an optional custom data JSON object, or tick **Raw JSON** and write the payload yourself. A read-only preview shows the payload as it will be sent (`{"aps":{"alert":{...},"badge":..,"sound":..,"category":..}, ...custom}`) with its size as `N / 4096 bytes` (UTF-8 bytes of the compact JSON; red above the limit, which the simulator refuses). Invalid JSON, a missing or empty `aps` or a non-numeric badge disable **Send**. Send writes the compact payload to a temporary file and runs `xcrun simctl push <udid> <bundle> <file>`; because simctl exits 0 for invalid JSON, success means exit 0 AND "Notification sent to ..."; otherwise simctl's error text is shown. "Sent" only means the simulator accepted the payload: a banner appears only if the app has asked for and been granted notification permission, which simctl cannot grant (Settings > Notifications in the simulator). **Android**: **Post** runs `adb shell "cmd notification post ..."` with title, text, a style (plain, big text, inbox lines, messaging with `who:text` lines) and a tag (posting again with the same tag replaces it). Every value is single-quoted for the device shell and sent as one command string (adb joins arguments and the device shell splits them again, so separate arguments would post the wrong title and tag); newlines in the fields are refused. This notification comes from the Android shell package (`com.android.shell`), not from your app, so it cannot test your app's own handling, channels or tap actions. **Clear shell notifications** cancels the shell package's notifications with `service call notification 1 ...` (there is no `cmd notification cancel`; the transaction number is version specific, so the tab lists the notifications afterwards and says when some remain). Android cannot send FCM messages from adb: use your backend or the Firebase console, or the **Send intent** group, which runs `am broadcast` with an action, a package or `package/.Class` component and extras (`key=value` per line, optional type prefix `i:`, `z:`, `l:`, `f:`; strings by default) so you can trigger your app's own debug receiver. `am broadcast` prints "completed: result=0" even when no receiver exists, so that does not prove delivery. Verified on a Pixel 9 emulator (Android 17) and an iPhone 17 Pro simulator (iOS 26.5) when scouting the commands and their error output (saved as fixtures); the payload building, quoting, parsing and history are unit tested. **Not verified**: the panel UI in the sandbox IDE, whether a banner shows once permission is granted, delivery when the app is not running, how individual `aps` keys beyond alert, badge, sound and category behave, Android bigpicture/media styles, icons and content intents, the clear call on other Android versions, an `am broadcast` to a real receiver with extras, and physical devices (not supported).

* The **Files** tab of Device Tools browses files on the device and the data of an app. **Location** is *Device storage* (Android starts in `/sdcard` and can go up to `/`; an iOS simulator shows its data folder) or *App data*, where you pick or type an app (package name or bundle id; the list comes from the Apps list, **Foreground app** fills in the app in front). A path bar with **Up** (never above the root of the location), **Refresh**, an editable path (Enter goes there) and **Copy path** sits over a table of Name, Type, Size and Modified (click a header to sort; folders always come first). Double click or Enter opens a folder; on iOS and for Android symbolic links a probe decides between folder and file. The buttons **Download** (you pick a folder, the file keeps its name, an existing file asks before it is replaced; the result line shows the local size), **Upload** (a chosen file into the current folder, always as `<folder>/<name>`), **New folder** and **Delete** (asks first and names the entry) are also in the right-click menu; a thin progress bar runs during a transfer. The **preview** on the right reads at most 256 KB: text, JSON (pretty printed), XML (pretty printed), Android **SharedPreferences** (`<map>` XML as a Key / Type / Value table, including string sets) and Apple **property lists** (iOS UserDefaults, binary `bplist00` or XML, as a Key / Type / Value table with nested keys like `a.b[0]`, dates as ISO text, `<data>` as hex) are shown; anything else says "Binary file" or "Too large to preview ... use Download". For a **SQLite** database the preview recognises the file header and offers **Pull and show in the file manager**, which pulls the database together with its `-wal`, `-shm` and `-journal` files from the same folder to a temp folder and reveals it, so you can open it in a database tool; there is no SQLite viewer in the plugin. How it works: Android uses adb only (`find ... -exec stat` for listings, `adb pull`/`push` for device storage, `adb shell run-as <package>` for app data), because mobilecli's `fs pull` reports success for a missing or unreadable file and writes the error text into the local file, and its other errors lose the reason; adb exit codes are checked and its messages are shown. **App data on Android works for debuggable apps only** (`run-as`); for others the message says "not debuggable" and suggests `/sdcard/Android/data/<package>` under Device storage. iOS simulators use `mobilecli fs ls|pull|push|mkdir|rm` with absolute host paths (the app container comes from `xcrun simctl get_app_container <udid> <bundle> data`; system apps have none). Downloading a folder works for Android device storage (adb pull) and on the simulator (recursive copy), not for an Android app's data. App ids may only contain letters, digits, '.', '_' and '-' (the id reaches the device shell). A download goes to a temporary name first and replaces the target only when it completed, so a failed or timed out download leaves no partial file and keeps an existing one; a changed device resets the tab to Device storage. Binary plists with more than 100,000 objects (self referencing or shared arrays) are refused. The temp folder of a pulled SQLite database is removed when the pull fails and kept on success (it is what the file manager shows). The first change in an app's data asks for a confirmation, as files written through `run-as` can break the app. Verified against a Pixel 9 emulator (Android 17) and an iPhone 17 Pro simulator for listing, push, pull, mkdir, delete, preview and `run-as` listing and reading, and the parsers against saved real output. Not verified: physical devices (a physical iPhone is not supported; physical Android should work but was not tried), the panel UI in the sandbox IDE (the logic is unit tested), a real iOS UserDefaults plist (the plist reader was checked against system property lists and plutil-generated samples), huge folders or files, names with line breaks or non-UTF-8 names, several users or work profiles on Android, and pulling a SQLite database with its WAL and opening it in a tool.

* The **Performance** tab of Device Tools charts memory, CPU and (Android) frame statistics of one app and measures its start time. **App** is *Foreground app* (re-read every 5 s with `mobilecli apps foreground`; needs mobilecli) or an installed app picked from the list or typed (package name or bundle id; letters, digits, '.', '_' and '-' only, because the id reaches the device shell). **Start** samples once per second on one daemon thread that never overlaps its own calls (a slow call delays the next sample, it does not pile up); **Stop**, a device change, closing the panel and Disconnect end it; **Clear** empties the charts; **Save CSV...** writes the samples (seconds, memory_mb, rss_mb, cpu_percent, fps, janky_percent; an empty cell is a gap). The newest 600 samples (10 minutes) are kept; the window combo shows the last 1, 5 or 10 minutes, and the readouts (now / min / avg / max, gaps ignored) cover the shown window. Hover a chart for a crosshair with the values. When the app is not running the lines stop and the status says so; polling continues, so sampling resumes by itself after a restart (the status then says "restarted"). Selecting another tab stops sampling too (the samples stay on the charts), so nothing polls the device while the tab is out of sight. Sampling adds load to the device being measured.
* The **Visual** tab of Device Tools is a screenshot diff (visual regression) that runs inside the plugin and needs no device command. **Save baseline** stores the mirror frame (the frozen one while Freeze is on) as `<project>/.mobiletestbench/baselines/<device name>/<name>.png` (the IDE system folder when the project has no base path) plus a `<name>.json` with the device, logical and frame size, time and ignore areas; saving over a name replaces the image and keeps its ignore areas (the tab asks for confirmation when the name already exists; selecting a baseline does not fill the Name field; an empty Name field is pre-filled with the foreground app id plus a timestamp, for example `com.example.app-20261007-1530`, or `screen-<timestamp>` on the home screen). Add `.mobiletestbench/` to your `.gitignore` or commit it to share baselines; names are sanitised so they cannot leave the folder. The list shows the baselines of the connected device (Delete, Refresh). **Update** replaces the image of the selected baseline with the current (or frozen) frame after a confirmation and keeps its ignore areas. **Rename** changes the name (image and json sidecar together, ignore areas kept) and refuses a name another baseline already uses. **Compare** diffs the selected baseline with the current frame and shows baseline | current | diff (changed pixels red over a faded current frame), a verdict line ("Match" or "N regions, X% of the pixels changed") and draws the changed regions on the mirror while the tab is open. The **Tolerance** slider (0 to 64, default 8, remembered) is the largest per-channel RGB difference that still counts as equal; an anti-aliasing allowance forgives a pixel that matches a neighbouring pixel of the other image, so a 1 px shift of a text edge is not a change (a 2 px shift is). Nearby changes are merged into one region (bounding box): the frame is cut into 8 px blocks and changes in the same or neighbouring blocks merge, so changes about 1 to 15 px apart merge depending on where they fall relative to the block grid, and changes 16 px or more apart never do and regions under 4 changed pixels are dropped as noise. If the baseline and the current frame differ in size (rotation, another device or scale) nothing is compared and the status says so. **Ignore** areas (device x, y, w, h in logical coordinates, the same as the inspector bounds) skip dynamic parts such as the status bar; they are remembered per baseline. Not verified on the devices: the comparison itself is covered by unit tests on generated images only, and the retina iOS frame scaling of the overlay and ignore areas was not checked against a real simulator.
  * **Android** (adb): one `adb shell` call per second reads `pidof`, `/proc/<pid>/stat`, `VmRSS` and the `dumpsys gfxinfo` counters. **CPU** is the delta of utime+stime (USER_HZ 100) over the device clock, in percent of ONE core (it can exceed 100 on a multicore device); the first CPU point appears after two samples. **Memory** shows PSS (blue) and RSS (yellow). PSS comes from `dumpsys meminfo`, which took 2 to 8 s on the emulator and once timed out with exit code 0, so it runs on its own task every 5 s (skipped while the previous call runs; the last value is held) and the 1 s loop never waits for it; RSS is read every second and is about twice the PSS for the playground app, so the chart names both. **Frames**: `Total frames rendered` and `Janky frames` are cumulative counters, so each second shows the delta: janky percentage (chart) and frames per second (in the title). An idle app renders no frames (fps 0, jank shown as a gap); a counter that goes down (app restarted, someone ran `gfxinfo reset`) re-baselines. For an app with several processes only the first pid of `pidof` is sampled. On the emulator used here everything was 100% janky because the host was overloaded, so these absolute numbers say little.
  * **iOS simulator** (the app is a normal macOS process): pid from `simctl spawn launchctl list`, memory is the physical **footprint** (`footprint -p <pid> -f bytes`; `ps` rss is far too high for a simulator app, 331 MB against 52 MB), CPU is the delta of the `ps` CPU time (10 ms resolution, so a 1 s window is accurate to about 1%; percent of one host core). There is no frame or jank source without Instruments, so the tab says so. Physical iPhones are not supported.
  * **Measure app start**: pick an explicit app (not *Foreground app*), **Kind** *Cold* or *Warm*, **Runs** 1 to 10 and press **Measure** (a dialog says the app will be stopped or sent to the background). The table shows run, kind, milliseconds and a note, **Average** gives average, min and max, the list under it keeps the last 20 measurements of this session (not persisted) with app and device, and **Cancel** stops after the current run. The first failed run stops the series. *Android*: cold = `am force-stop`, 1.5 s, then `am start -W` with the launcher intent (`-a MAIN -c LAUNCHER -f 0x10200000 -n <pkg>/<activity>`, activity from `cmd package resolve-activity`) and its **TotalTime**; warm = Home key, 2 s, the same command (a plain `am start -n` after Home only brings the task to the front and prints no TotalTime; if the app is not running a warm run first launches it untimed). The note shows the LaunchState (COLD or WARM) and flags a mismatch. `mobilecli apps launch` is not used: it prints no timing and returns after about 1.5 s whatever the app is doing. *iOS simulator*: cold = terminate (an app that is not running is fine), 1.5 s, `simctl launch`; warm = Home button (through mobilecli, needed for warm), 2 s, launch. Timing comes from the simulator log: the "Requesting launch of ..." line to the last UIKit "Deactivation reason ... -> 0" line of the app process, which means UIApplication became active (not first frame, and including about 0.4 s of launch animation); it needs a 2.5 s settle delay plus about 1 s for `log show` per run. This reads undocumented UIKit debug text, so when the lines are not found the note says "fallback" and the number is only the duration of the `simctl launch` call, which times the spawn and nothing else. Cold starts on the emulator took 9 to 34 s here because the host was loaded, so a 10 run series can take minutes and timings depend on host load.
  * Verified: the parsers and the sample, statistics, start and CSV logic against real output of an Android emulator (Android 17) and an iPhone 17 Pro simulator (iOS 26.5), and every command by hand during scouting. **Not verified:** the panel in the sandbox IDE (chart painting, hover, the thread handling; the logic is unit tested, the Swing code is not), physical devices (`dumpsys meminfo` is normally much faster there; real-device jank values and the USER_HZ of 100 were not seen), apps with several processes, the iOS log timing on other Xcode or iOS versions, with scene based apps or launch storyboards, and after the app was suspended for a long time, and sampling while the mirror and the inspector are busy on a loaded host.

* **Screenshot** (the eye icon): copy the current screen to the clipboard or save it as a PNG (the file name has the device and the time). With an element selected in the inspector you can also choose the variants that outline that element in the picture, handy for bug reports. The last menu entry toggles "Also save the hierarchy (XML) next to the PNG" (remembered): Save as PNG then also writes `<name>.xml` with the same base name, the UI tree of the connected device (the frozen hierarchy while Freeze is on, else the last one read, else a fresh read) with the device attributes and bounds as x/y/width/height. Not verified on a device; the XML writer is unit tested.

### Device Power (boot, shut down, reboot)

The device list also shows devices that are not running, greyed out and marked "(offline)": stopped Android AVDs and shut-down iOS simulators (from `mobilecli devices --include-offline`, so mobilecli is needed). Selecting one shows "Device is offline" in the screen area; Connect stays disabled. The **Device Power** button (lightning icon) opens a menu for the selected device:

* **Boot** (offline devices only) runs `mobilecli device boot`, which waits until the device is usable (about 8 s for a simulator, 30 s or more for a cold AVD; the timeout is 120 s). The plugin then looks every 2 s, up to 60 s, for the device in the list (an emulator is recognised by its AVD name, because its adb serial changes) and shows a notification "... booted. Connect to it?" with a **Connect** button. It never connects on its own. On a timeout the notification says to press Refresh Devices.
* **Shut Down** and **Reboot** (running emulators and simulators only) ask for confirmation first. If the device is the connected one, the session is disconnected before the command runs. Shutdown is a hard stop. With **Reconnect automatically** on (the default) a connected device that is shut down or rebooted from here is waited for and connected again by itself once it is back (see Reconnect automatically); with it off, the plugin waits after a reboot and offers Connect, like after a boot.
* The button is disabled while an operation runs, and the status line shows what is happening ("Booting Pixel 9...", "Waiting for ... to come up..."). Errors show mobilecli's own text (for example "simulator is already running").

Limitations and what is not verified:

* mobilecli lists only AVDs that have an `avd.ini.displayname` line in their `config.ini` (Android Studio adds it; AVDs made by hand may lack it), and only simulators that were booted at least once. Others are not shown and cannot be booted here.
* Verified with real mobilecli output: the offline list, boot and shutdown of an iOS simulator, boot and shutdown of a temporary Android AVD, and the error texts. Not verified: `device reboot` (never run; whether it waits, whether an emulator keeps its serial, and the iOS simulator behaviour are unknown, so a short fixed pause plus polling is used), boot of an AVD you actually use, a warm snapshot boot, offline physical devices (not listed), and boot from an IDE started with a minimal environment (mobilecli needs to find the emulator binary). The UI itself (menu, dialogs, notification) has not been run, and no state is saved when an emulator is shut down.
* Booting a second emulator next to a running one uses a lot of memory and CPU.


### Reconnect automatically

When the connected device goes away without you pressing Disconnect (emulator or simulator restarted or shut down, a reboot, adb going offline) the status line shows "Waiting for <device> to come back..." with a **Cancel** link, and the panel connects again by itself once the same device is listed as usable. A normal connect then follows: the hierarchy, the Device Tools tabs and the logs reload. How it works:

* While connected, discovery (the same one as Refresh Devices) is polled every 3 s. The device counts as gone when it is missing or not usable in two polls in a row; a session error counts as one missed poll. A failing discovery (for example adb not answering) changes nothing: discovery reports failures as warnings, so a result with warnings that does not list the device as usable counts as inconclusive, not as a missed poll.
* While waiting, the poll interval grows from 3 s to 10 s. There is no time limit. The device is matched by id, or for an Android emulator by AVD name, because the adb serial can change between boots.
* Disconnect, Cancel, choosing another device in the list and closing the tool window all end the wait. If the device is listed again but connecting fails (still booting), the plugin keeps waiting.
* Device Power Shut Down or Reboot of the connected device does not fight the watcher: it pauses while the power operation runs, then reconnects once the device is up. After a shutdown the panel keeps waiting until you boot the device again (press Cancel if you do not want that).
* Settings | Tools | Mobile Test Bench has a **Reconnect automatically** checkbox (default on). It is read when a connection is made; turning it off does not end a wait that already started (use Cancel).

Not verified against the live sandbox: the logic is unit tested with a fake discovery and clock (`ReconnectTest`), but the panel glue (status line, Cancel link, session teardown, reconnect after a real emulator restart or Device Power reboot) was only compiled, not run.

### Project state and live foreground app

* The panel remembers, **per project** (stored in the project's workspace file, `.idea/workspace.xml`, not in the application settings): the last connected device (id and name), whether the inspector was open, whether Device Tools was open and which tab was selected, and the splitter proportions of the mirror/inspector and of the mirror/Device Tools split. They are restored when the tool window opens, saved about one second after a change and when the panel is disposed. A saved tab that no longer exists is ignored, and invalid proportions fall back to the defaults.
* After the first device refresh the last device is pre-selected in the device combo when it is among the discovered ones (same id, else same name, because an emulator serial changes between boots). It is only selected, not connected, unless **Settings | Tools | Mobile Test Bench | Reconnect to the last device when the project opens** is on (default off); then it connects when that device is running.
* A label at the right end of the status area shows the **foreground app** (name and package/bundle id, "Home screen" on the iOS home screen, a dash when it cannot be read). While a device is connected and the tool window is visible it is read every 3 seconds with `mobilecli apps foreground` on a pooled thread, one call at a time (6 s timeout). Polling stops on disconnect, when the tool window is hidden and on dispose, and a result that arrives for an older generation or another device is dropped. Click the label to copy the package id; the tooltip shows the activity on Android.
* Not verified: the label and restore against the live devices in the sandbox IDE (the code is covered by unit tests, a platform test of the project service and the tool window smoke test), mobilecli's output for apps that have no `appName`, and polling load on a slow device (the on-device agent may be slow; a timeout shows the dash).

### Orientation

The "Landscape" toggle in the toolbar rotates the device between portrait and landscape through `mobilecli device orientation` (needs mobilecli). The toggle shows the real orientation: it is read from the device on connect and after every change, never assumed. After a rotation the click mapping, the inspector bounds and the recorder geometry use the new size, and the hierarchy reloads when the inspector is open. On an iOS simulator the framebuffer stays portrait, so the plugin turns frames upright itself. Limitations: mobilecli switches Android auto-rotate off when it sets an orientation and it stays off. Unverified: the Android gRPC frame in landscape, iOS inspector bounds for ordinary apps in landscape, taps in landscape, and physical devices.

### Page objects

**Generate Page Object...** (the class icon in the toolbar, enabled once the inspector has loaded a hierarchy) writes a page object class for the current screen:

* A table lists the visible elements that have a **unique** locator, with the controls (buttons, fields, switches) ticked and plain texts offered but not ticked. Elements without a unique locator are shown greyed out and cannot be ticked. Names are suggested from the test id, label or text (`email input field`, `login button`) and can be edited; they are made unique within the class.
* Pick the framework and language: **Mobilewright** (TypeScript, JavaScript) or **Appium** (Java, Kotlin, Python, C#), and the class name. The code below the table updates as you change anything.
* **Locators** says where the locators live:
  * *Fields, screen/driver from the base class* (default): all locators are private fields grouped at the top, and the page object has no constructor of its own because the base class holds the Mobilewright `screen` or the Appium `driver`. In Java, Kotlin and C# that is a one-line constructor passing the driver on (`super(driver)`).
  * *Getters*: private getters or properties instead of fields, also with the screen or driver from the base class.
  * *Fields, set in the constructor (no base class)*: a class that stands alone and builds its locators in its own constructor.
* **Base class**: the generated page extends `BasePage`. The base class is generated too (second tab). Type your own name to extend a class you already have and untick **Generate the base class**; the name is remembered, together with the language, the locator style and the sort setting. An own base class has to expose the screen as `screen` (`this.screen`) or the driver as `driver` (`Driver` in C#).
* Locators are **private**, and the generated class has one comment saying so: make a locator public only when a test needs it, for example in an `expect`.
* **Sort by name** orders the locators and their methods alphabetically.
* Each element gets its locator and the methods that fit it: `tapX()` for controls, `fillX(text)` and `getXValue()` for input fields, `getXText()` for texts. Appium locators are `By` descriptors (not `WebElement`s, which go stale).
* Locators are the best unique ones the Locators tab shows. Mobilewright uses the "in parent" variant for duplicated ids, so a repeated `add-to-cart` button works. Appium prefers `id`, then `accessibility id`, then UiSelector or the iOS predicate/class chain, then the XPath (also the one in a parent).
* **Copy**, **Insert at Caret** and **Save...** work on the tab you are looking at (Python files are saved as `login_page.py`).
* The Appium code follows the current Java, Kotlin, Python and .NET clients and the Mobilewright code its documented API (`getByTestId`, `tap`, `fill`, `getText`, `getValue`); check the imports against your versions, in particular the `Screen` import in the TypeScript output.

### Recorder

Press **Record** (the red dot in the toolbar) and use the device: the **Recording** tab turns what you do into Mobilewright code.

* A tap becomes `await screen.getByTestId('login-btn').tap();`. The plugin reads the hierarchy right before the tap, finds the element under the finger and picks its most stable locator: a unique test id (also from a parent button or cell when you tap its text), then any unique `getByRole`, `getByLabel` or `getByText`, then the same locator scoped by a unique parent (`screen.getByTestId('product-item-2').getByTestId('add-to-cart')`), and as a last resort the first locator with `.nth(n)`. The hierarchy is captured in the background (after the device has been quiet for 0.3 s following an action, and every second while idle), so a tap normally does not wait. mobilecli dumps take anywhere from 0.1 to several seconds, so a tap waits at most 2 s for a hierarchy taken after your previous action; after that it uses the newest older one and the line ends with `// check: matched against the screen before the previous action`. Typing does not invalidate the hierarchy. `idea.log` records every capture and how long each tap waited. A screen that changes by itself in the second before a tap can still be matched against the older hierarchy.
* Typing after a tap on a field turns the tap into `.fill('text')`, and Backspace edits that text.
* Swipes and scrolling become `await screen.swipe('up')` (the direction of the finger), Home becomes `screen.pressButton('HOME')` and Back on Android `screen.goBack()`.
* Taps that cannot be tied to a locator are written as a comment, never as raw coordinates.
* **Copy**, **Insert at Caret** and **Clear** work on the recorded code. Stopping the recording keeps the code.
* **Assert** (while recording) adds an assertion instead of an action: press it, click an element on the screen (it is not tapped on the device), and choose from a menu that fits the element: *Is visible*, *Has text 'x'*, *Contains text 'x'*, *Has value 'x'* (input fields), *Is enabled / disabled*, *Is checked* (switches and checkboxes). It is recorded as `await expect(screen.getByTestId('title')).toHaveText('Welcome');`, so the test needs `expect` from `@mobilewright/test`. Mobilewright assertions retry until they hold, so they also act as explicit waits. The element under the cursor is highlighted while Assert is on. The menu also has *Becomes hidden* (`await expect(loc).toBeHidden();`; an element that left the screen counts as hidden), explicit waits *Wait until visible / hidden / enabled / disabled* (`await loc.waitFor({ state: 'hidden' });`, same rules as Mobilewright: hidden also holds for a missing element, disabled needs the element to exist) and, only when the locator matches two or more elements on the screen, *Count of matching elements = N* (`await expect(loc).toHaveCount(3);`, N is prefilled and editable, and the locator is written without `.nth()`). The semantics of `waitFor`, `toBeHidden` and `toHaveCount` were read from the installed Mobilewright package code, not run against it, and the generated code was not executed by Mobilewright.
* **Output** (combo in the Recording tab, remembered): *Mobilewright* (default), *Appium Java*, *Appium Kotlin*, *Appium Python*, *Appium C#* or *Appium JavaScript (WebdriverIO)*. Recording and replay do not change; the same steps are only written in the chosen language in the list, **Copy** and **Insert at Caret**. Each step carries the best unique Appium locator of its element, computed from the same hierarchy when it is recorded (`id`, then `accessibility id`, `-android uiautomator` / iOS predicate / class chain, `xpath (in parent)`, `xpath`, the same choice as the Generate Page Object dialog). A step whose element has no unique Appium locator is written as a comment that says so (never as coordinates).
  * WebdriverIO output: `await $(...).click()`, `setValue(...)`, `expect($(...)).toBeDisplayed()` / `toHaveText(...)` assertions and `waitForDisplayed({ timeout })` / `waitForEnabled` waits; gestures use `driver.execute('mobile: ...')` like the other flavors. The code assumes `$`, `driver` and `expect` from `@wdio/globals` (a leading comment names the import). A count assertion is a comment, as in the other Appium flavors.
  * Conventions: the code assumes a `driver` and, for waits and asserts, a `wait` (a `WebDriverWait` of 10 s); when a recording needs them, leading comment lines show the declaration and the import. Tap is `driver.findElement(By.id("x")).click();`; fill is `clear()` then `sendKeys(...)` (Mobilewright `fill` replaces the text); *Is visible* and the waits use `ExpectedConditions` (Java, Kotlin, Python `expected_conditions`; C# uses `wait.Until(d => ...)` lambdas because `ExpectedConditions` is no longer part of Selenium .NET); text, contains, value, enabled and checked are asserts on the visible element: JUnit 5 `assertEquals` / `assertTrue` (Java, Kotlin), plain `assert` (Python), NUnit `Assert.That` (C#). Becomes hidden is `invisibilityOfElementLocated`. Scroll until visible is a bounded loop of swipes. Back is `driver.navigate().back()`, Home is `mobile: pressKey` (Android) or `mobile: pressButton` (iOS).
  * Gestures use the Appium `mobile:` commands of the recorded platform, because no single form works on both: Android UiAutomator2 `mobile: longClickGesture`, `doubleClickGesture` and `swipeGesture` (the whole window, 75 %); iOS XCUITest `mobile: touchAndHold`, `doubleTap` and `swipe`. A recording is for one platform, so the output is too.
  * Not written as Appium code: *Count of matching elements* (the unique Appium locator matches one element) and a drag with hold; both stay comments.
  * Verified: the `mobile:` command names and argument names (UiAutomator2 `docs/android-mobile-gestures.md`, `README.md` and the XCUITest `execute-methods.md` on GitHub), the `executeScript` forms in the Java, Python and C# examples of those docs, and the locator strings (shared with the Locators tab). Not verified: none of the generated code was compiled or run against an Appium server; the swipe direction meaning of `swipeGesture` (assumed to be the finger direction, as in Mobilewright), the 75 % distance (a guess), `RemoteWebElement.getId()` / C# `WebElement.Id` / Kotlin `id` for the element id on your client versions, the C# `MobileBy` names (see the Locators tab note), and that `WebDriverWait` ignores a missing element in the wait lambdas.
* **Replay** runs the recorded steps again on the connected device, with the running step highlighted and finished steps marked passed, failed or skipped. Like Mobilewright, each step waits (up to the replay element timeout, default 10 s) for its element to show up in the hierarchy and then acts on its center; assertions retry for up to that timeout (or the step's own timeout; see Replay controls and Step timeouts below) and fail with what the element had instead; the first step that fails stops the replay and shows why. `fill` taps the field, clears it and types the text: it presses select all + backspace in one mobilecli call (`cmd+a` on iOS, `ctrl+a` on Android; ctrl+a on iOS only moves the cursor) and reads the field back, and like Mobilewright it fails the step with "Failed to clear element" when text is left, instead of appending. Clearing was verified with mobilecli on native text, password and multiline fields only; custom widgets (React Native, Flutter, WebViews, Compose) may ignore select all, and an iOS simulator without mobilecli (WebDriverAgent only) cannot clear, so `fill` fails there. On Android, text equal to the field's `hint` attribute counts as empty (uiautomator reports the hint as text); a uiautomator dump without a `hint` attribute cannot be told apart and was not verified. Waits and assertions poll like `expect`, swipes use the middle of the screen, comments are skipped, and **Stop** cancels the run. The recording and the device must be the same platform. Your own clicks are ignored while a replay runs.
* **Replay controls**: *Replay* runs everything. *Replay from Step* (button, or right-click **Replay from this step**) runs the selected step and everything after it; with several rows selected it starts at the first one. *Replay Selected* (button, or **Replay selected steps**) runs from the first to the last selected row (a selection with gaps replays the gaps too). Highlighting and result marks use the real row numbers, steps outside the range keep no mark, and the run still stops at the first failure. Starting in the middle assumes the app is already on the right screen. Two settings in Settings | Tools | Mobile Test Bench, group *Replay*: **Replay element timeout (seconds)** (default 10, 1 to 300) is how long a step waits for its element, wait or assertion when the step has no timeout of its own, and **Delay between steps (ms)** (default 0, 0 to 10000) pauses between two steps that run, for slow motion (not before the first step, not for skipped comments). The settings are read when a replay starts.
* **Step timeouts**: right-click a wait, expect or count step (several can be selected) and choose **Set timeout...**, then type whole seconds (1 to 3600); an empty answer removes it and the replay timeout setting applies again. Scroll until visible has no timeout (its limit is its swipe count). The timeout is part of the step in every output language: Mobilewright `await loc.waitFor({ state: 'visible', timeout: 30000 });` and `await expect(loc).toHaveText('x', { timeout: 30000 });` (also `toHaveCount(3, { timeout: ... })`); Appium uses a dedicated wait for that step, e.g. Java `new WebDriverWait(driver, Duration.ofSeconds(30)).until(...)`, Kotlin `WebDriverWait(driver, Duration.ofSeconds(30))`, Python `WebDriverWait(driver, 30)`, C# `new WebDriverWait(driver, TimeSpan.FromSeconds(30))`; the count assertion has no Appium form. Replay uses the step timeout instead of the setting. Not verified: the Mobilewright `timeout` option names were taken from the Mobilewright skill docs (`waitFor({ state, timeout })`, `toBeVisible({ timeout })`) and applied to the other matchers by analogy, they were not run against Mobilewright; the Appium forms were not run against an Appium server; nothing was tried on a real device (fake sessions in tests). Appium output rounds a timeout up to whole seconds.
* **Scroll until the next element is visible**: select one or more swipe steps in the list (shift/ctrl click), then press the **Scroll Until Visible** button or right-click and choose the menu entry. The swipes must be next to each other, go the same direction and be followed by a step on an element (tap, long press, double tap, fill, or an expect or wait that wants the element visible; "is hidden" or "not visible" steps are rejected). They are replaced by one step, written as `for (let i = 0; i < 10 && !(await loc.isVisible()); i++) { await screen.swipe('up'); }`, with the element step kept after it. The limit is 10 swipes, or the number of swipes you selected when that is higher. Replay checks the hierarchy before the first swipe and after each one (the same swipe as a Swipe step, with a short pause for the scroll to settle) and stops as soon as the element is visible and its center is on the screen; if the hierarchy cannot be read it does not swipe but retries until the element timeout; after the limit it fails with "did not become visible after N swipes up". Not verified: the generated `isVisible()` loop was not run by Mobilewright (it is the locator method as named in the brief), and the replay was tested with fake sessions only, not on a device. To change the direction (up, down, left, right) or the limit (1 to 100 swipes), right-click the scroll step and choose **Set scroll direction and limit...**; the generated code in every output language follows. The dialog itself was not tried by hand, only the core logic is unit tested.
* While recording, clicks act on the device (they do not select elements, as they do when only inspecting).
* Mobilewright code only for now. Replay uses the plugin's own device control, not Mobilewright: it does not run the generated code.

### Freeze

The **Freeze** toggle (pause icon) stops the mirror on the current frame so you can look at a transient screen such as a toast, snackbar or loading state. While it is on:

* New frames are dropped (not queued) and a "Frozen" badge is drawn on the screen; the session itself keeps running.
* Clicks, typing, keys and the scroll wheel do not reach the device; the status bar says so. A click in inspect mode selects the element from the frozen hierarchy.
* Turning Freeze on at once captures the hierarchy of that moment in the background and shows it in the inspector (the inspector opens if it was closed). The automatic refresh is paused, so the tree stays the one of the frozen screen.
* Screenshot, copy and Generate Page Object use the frozen frame and hierarchy.

Turning it off resumes live frames and refreshes the hierarchy if the inspector is open. Disconnecting clears the freeze. Not verified: whether the hierarchy capture is fast enough on a real device to catch a toast that disappears within a second or two, and a running replay is not blocked by Freeze.

### Coordinates, hover info and grid

* **Hover line.** Under the mirror, above the status line, a line shows what is under the mouse while a device is connected: the device coordinates in logical units (points on iOS, pixels on Android), the pixel of the frame image when its resolution differs from the logical space (iOS retina), the position in percent (`x%, y%`, one decimal, taken from the middle of the logical unit) and, when a hierarchy is already known, the deepest element at that point (type, text or label, `#id`) with its size `w x h`. The hierarchy is the one the inspector loaded or froze, else the newest recorder snapshot. Hovering never fetches a hierarchy: with none loaded the line says so, and an element can be stale after the screen changed until the inspector refreshes. The line is separate from the fps status line.
* **Grid** (toolbar toggle, remembered). Draws a light grid over the mirror with the logical coordinate at the top and left edges, and a crosshair through the cursor labelled with its coordinates. The step is chosen from the logical size so that the longer side has at most 12 lines (smallest of 10, 20, 25, 50, 100, 200, 250, 500, 1000, 2000), for example 100 on an iPhone (points) and 200 on a Pixel (pixels). The brief said 50 or 100; larger steps are needed to keep a 2400 px Android screen at about 12 lines.
* **Copy menu.** Right click (or Ctrl+click on macOS) on the mirror opens a menu with `Copy "x, y"`, `Copy "x%, y%"` and, when the hierarchy has an element there, `Copy element size "w x h"` and `Copy element bounds "x, y, w, h"` (logical coordinates, the same as the inspector). The menu only reads, so it is offered in every mode (inspect, recording, assert, frozen). A right click is never a tap any more (before this it was sent like a left click) and does not select in inspect mode.
* **Tap marker.** A tap, double tap or long press that is sent from the mirror draws a ring with its logical coordinates for about a second at the spot. Clicks in inspect mode (selecting), while frozen, or during a replay are not marked.

Not verified: the overlay and the menu were not tried by hand on the running devices (only unit tests of the mapping, formatting and grid step and the tool window smoke test), a safe-area inset overlay is not implemented, and the hover line was not checked against a rotated iOS frame.

### Inspector

Toggle **Inspect Elements** (the target icon) to open the inspector next to the screen:

* **Element tree** with speed search (just start typing) and a filter above it: type text to keep only elements whose type, id, label, text or value contains it (their parents stay), and tick **Visible** or **Interactive** to hide invisible or non-actionable elements. The field also takes attribute terms next to free text, separated by spaces and all required to match: `key=value` (equals), `key!=value` (not equal) and `key~value` (contains), all case-insensitive, for example `clickable=true enabled=false class~Button text~Login`. Put a value with spaces in double quotes (`text="Log in"`). These keys work on Android and iOS: `enabled`, `clickable`, `focused`, `checked`, `selected`, `visible`, `interactive`, `checkable`, `focusable`, `scrollable`, `password`, `long-clickable` (true or false; a missing attribute counts as false, and `clickable` on iOS means a control type), `type` or `class` (short or full name), `id`, `identifier`, `resource-id` or `resourceid`, and `label`, `text`, `content-desc`, `contentdesc`, `desc` or `value` (these four all look at the label, text and value of the element). Any other key is read from the raw attribute (for example `package=com.example`, `index=0`). A term that cannot be applied (`=x`, `enabled=maybe`, an open quote) is listed in red under the field as not understood and does not filter. Besides that: a word with a leading `-` or `!` is negated (`-error`, `-clickable=true`, `-/spinner/`); a case-insensitive regular expression between slashes is matched against type, id, label, text and value (`/^btn_(ok|cancel)$/`; quote it if it contains spaces: `"/log in|sign in/"`); and `OR` (or `|`) starts a new group, so `type=Button OR type=TextField` or `login OR /sign ?in/` shows elements that match any group (all words inside a group must match). An invalid regular expression is reported under the field and ignored. Bare uppercase `OR`, `|`, words starting with `-` or `!` (except `!=`) and words written `/x/` are operators now, not free text; quote them to search for the literal text. The last filter text is remembered between sessions (setting `elementFilter`). Hover the field for the syntax. Verified by unit tests on the sample hierarchies only, not yet by eye on a live device. It refreshes by itself shortly after you send input to the device.

* **Right-click an element in the tree** to copy any of its locators (every Mobilewright and Appium strategy shown in the Locators tab) or **Copy All Properties** (type, bounds, XPath and all raw attributes as `key=value` lines).
* **Hover** over the screen to highlight the element under the cursor; **click** to select it in the tree.

A status line above the table says what could be checked (`Density 420 dpi (2.63x) - frame sampling on`, `Density unknown: Android size rules skipped`, `no frame: contrast skipped`), the **Contrast hints** checkbox (remembered) switches the contrast estimate off, and the **Kind** column colors AA failures red, guidance orange and hints gray. Below the recommended size is guidance only, not an AA failure: 44 x 44 pt on iOS (Apple, WCAG AAA 2.5.5), 48 x 48 dp on Android (Material). iOS bounds are points. Android bounds are pixels, converted to dp with the screen density (`adb shell wm density`, an override wins, read once per connection; if it cannot be read the Android size rules are skipped and the status line says so). The 24 dp spacing circle is measured in dp too. Android SeekBars are not clickable in the dump, so they are not audited at all.

Pixels are grouped by their top 5 bits per channel; the background is the biggest group, the text color the group with the highest contrast against it, and both colors are the exact mean of their pixels. The message shows the ratio and both colors. Large text only needs 3:1, but the dump has no font size, so 4.5:1 is used. Because anti-aliased text makes the estimate slightly low, only ratios below 4.4 are reported. Contrast of icons and other non-text parts (SC 1.4.11) is not checked.

### Locators in the editor

**Show Locator on Device** (editor context menu, Tools menu, shortcut Ctrl+Alt+Shift+M) takes the selected text, or the line with the caret when nothing is selected, finds the locator in it, and tries it on the screen of the device connected in the Mobile Devices tool window. Examples it understands: `await screen.getByTestId("a").tap()`, `driver.findElement(By.id("x")).click()`, `self.driver.find_element(AppiumBy.ACCESSIBILITY_ID, "y")`, `LOGIN = (AppiumBy.ID, "x")`, `"xpath=//Button[@name='b']"`, `"id=com.x:id/y"`, a quoted XPath string, and a selection made inside an XPath. Only the locator is cut out (the `.tap()` or `.click()` is ignored); the evaluation is the same as the Locators tab playground (Mobilewright chains, XPath, all the Appium forms), so the same things are refused.

* The hierarchy is read fresh from the device on a background thread (the editor does not wait), unless the screen is frozen: then the frozen hierarchy is used.
* Every match is highlighted in green on the mirror; the highlight stays until you send the next input to the device (or the inspector refreshes). With the inspector open, the tree is refreshed and the first match is selected.
* The result is shown as an IDE balloon and in the viewer's status line for a few seconds: `3 matches`, `1 match (unique)`, `no match`, `not supported: ...`, `no locator found ...` or `no device connected: connect one in Mobile Devices`. If the tool window was never opened, the action opens it (and says no device is connected until you connect one).
* The viewer registers itself with a project service (`LocatorTargets`), which is how the action reaches it.
* Not verified: the shortcut is only checked not to clash with the defaults I know, not against every keymap; the action was tested without a device (extraction, evaluation on sample hierarchies, registry, enabled state, the tool window still builds) but not clicked in a running IDE against a live device. Locators spread over several lines must be selected; locators in variables or constants are not followed.

## Getting started

Requirements: JDK 21 and an Android SDK. Xcode is only needed for iOS.

```bash
./gradlew runIde      # starts a sandbox IDE with the plugin
./gradlew test        # unit tests for parsers, locators, geometry and the MJPEG reader
./gradlew buildPlugin # zip in build/distributions, installable via "Install Plugin from Disk"
```

`gradlew` is executable now. `sh gradlew ...` works as well, and Windows uses `gradlew.bat`. Or open the folder in IntelliJ IDEA and run the Gradle task `runIde`. The first build downloads the IntelliJ Platform, so it takes a while.

In the sandbox IDE, open the **Mobile Devices** tool window on the right, pick a device and press **Connect**.

### Android

* Start an emulator (Device Manager or `emulator -avd <name>`) or connect a device.
* adb is found via the adb path setting, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `~/Library/Android/sdk` or `PATH`.
* The gRPC port and token are read from the emulator discovery files (`~/Library/Caches/TemporaryItems/avd/running/pid_*.ini` on macOS), the same mechanism Android Studio uses.

### iOS simulator

* Boot a simulator.
* With [mobilecli](https://github.com/mobile-next/mobilecli) installed (`npm install -g mobilecli`) the simulator works like an iOS device: screen, input and inspection go through mobilecli, no WDA needed.
* Without mobilecli, input and inspection need **WebDriverAgent** running on that simulator. Two ways to start it:
  * Start an Appium XCUITest session once; Appium keeps WDA running on port 8100, with MJPEG on 9100.
  * Or build and run WDA directly:

    ```bash
    xcodebuild -project WebDriverAgent.xcodeproj -scheme WebDriverAgentRunner \
      -destination "platform=iOS Simulator,id=<udid>" test
    ```
* Without mobilecli and WDA you still get the screen (simctl screenshots) but no input or hierarchy.
* The WDA URLs (only used without mobilecli) are configurable in **Settings | Tools | Mobile Test Bench**.

### iOS device (physical, via mobilecli)

* Install [mobilecli](https://github.com/mobile-next/mobilecli) (`npm install -g mobilecli`). It is found on the IDE's `PATH`, then `/opt/homebrew/bin` and `/usr/local/bin`. Without it physical devices are simply not listed.
* Connect and trust the device; it then shows up as `[physical]`. Devices are listed with `mobilecli devices --platform ios --type real`.
* Input and inspection use mobilecli's on-device agent. For a real device it may need installing first (`mobilecli agent install --device <id> --provisioning-profile <file>`, see `mobilecli agent install --help`). The plugin does not do this for you, but when mobilecli reports `agent is not installed` the status line shows the full setup (command with your device id, matching development provisioning profile, Developer Mode, trusting the certificate).
* Only Home, volume, Enter and Backspace are available as keys; Back, Recent Apps and Power are not.

## Install, build and release

### Install from disk

Build the zip with `./gradlew buildPlugin` (result: `build/distributions/MobileTestBench-0.1.0.zip`, about 11.7 MB, with `LICENSE` and `NOTICE` inside). In the IDE open Settings, Plugins, the gear icon, **Install Plugin from Disk...** and pick the zip. You need `mobilecli` on the PATH, `adb` for Android and Xcode for iOS simulators.

To let someone else try it, send them the zip together with `TESTING.md` (requirements, install steps, things to try, what is unverified and how to report a problem).

### Build and verify

* `./gradlew test` runs all tests.
* `./gradlew buildPlugin` builds the zip. The change notes come from `CHANGELOG.md` (section of the current version), the description from `plugin.xml`, since-build 253 with no until-build. The build fails with an error if CHANGELOG.md has no section (or no bullets) for the current version, so the Marketplace never gets empty change notes.
* `./gradlew verifyPlugin` runs the IntelliJ Plugin Verifier against the recommended IDEs (`pluginVerification { ides { recommended() } }`). It downloads several IDEs and takes about 5 to 6 minutes. Last run (IU 253, 261, 262, 263): compatible everywhere, 16 deprecated-API usages (14 are overrides in the generated emulator protobuf code, 2 were the varargs `FileSaverDescriptor` constructor in the log and crash save dialogs, since replaced by `FileSaverDescriptor(title, description).withExtensionFilter(...)`, not yet re-verified), no experimental, internal or scheduled-for-removal usages.
* `META-INF/pluginIcon.svg` (40x40) and `pluginIcon_dark.svg` are the Marketplace icons.

### Sign and publish

Signing and publishing read environment variables only; no value is stored in any file.

```bash
export CERTIFICATE_CHAIN="$(cat chain.crt)"
export PRIVATE_KEY="$(cat private.pem)"
export PRIVATE_KEY_PASSWORD='...'
./gradlew signPlugin
export PUBLISH_TOKEN='...'
./gradlew publishPlugin
```

Without the variables `signPlugin` is skipped and `publishPlugin` fails before uploading anything. **Nothing has been signed or published.** The behaviour with real credentials is unverified.

## Architecture

```
core/                      IDE independent, unit tested
  Model.kt                 Device, Size, Rect, DeviceKey
  ScreenGeometry.kt        panel <-> device coordinate mapping (letterboxing, retina)
  exec/                    process runner, adb/xcrun lookup
  discovery/               adb devices -l, simctl JSON and mobilecli devices parsers
  power/                   Device Power: boot/shutdown/reboot actions, offline device parser and merge, polling
  session/DeviceSession    common interface: frames, input, hierarchy
  android/                 AdbClient, AndroidSession, emulator discovery files
  ios/                     SimctlClient, WdaClient, MobilecliClient, MJPEG reader, IosSimulatorSession, IosMobilecliSession
  inspector/               UiNode, uiautomator, WDA and mobilecli dump parsers, locator generation, tree filter query
  input/                   Gestures (mouse rules), Input (hardware buttons, keys, clipboard)
  recording/               ScriptRecorder, ScriptPlayer, assertions, scroll until visible
  freeze/ reconnect/       FreezeState, ReconnectWatcher
  apps/ permissions/ crashes/ location/ display/ network/ battery/ biometrics/ webview/ files/ perf/ visual/ notifications/   logic of the Device Tools tabs
android/GrpcEmulatorLink   emulator gRPC (generated from src/main/proto/emulator_controller.proto)
settings/                  persistent settings + Settings page
ui/                        tool window, ScreenView (rendering + input), InspectorPanel
```

Coordinates: input and hierarchy bounds use a "logical" space per platform (pixels on Android, points on iOS). Frames can have a different resolution, so the view maps through normalized coordinates (`ScreenGeometry`).

`emulator_controller.proto` comes from AOSP (`platform/external/qemu`, Apache 2.0).

## Status and known limitations

* **Tested so far:** the `core` package has unit tests (parsers, locators, locator query, accessibility rules, sessions with fake processes). The plugin has been run in a sandbox IDE (`./gradlew runIde`) against an Android emulator (gRPC) and an iOS simulator (mobilecli). Also run against a physical iPhone 13 (iOS 27) and a Samsung Z Fold8 Ultra (Android 17): mirror, tap, swipe, long press, text input and the inspector, and the Fold's display switch when folding.
* **gRPC frames:** the emulator sends uncompressed RGB888 frames at native resolution. Requesting a scaled `ImageFormat` would reduce CPU use.
* **WDA URL (fallback only, used when mobilecli is missing):** there is one WDA URL for all simulators. Running several simulators at once needs one WDA port per device.
* **mobilecli** was checked at 1.0.14 (help output) and again at 1.0.17 against an Android emulator and an iOS simulator: devices, device info, UI dumps, screenshots, tap, swipe, text, keys, buttons and the MJPEG stream. **Physical devices** (an iPhone 13 on iOS 27 with the agent installed, and a Z Fold8 Ultra on Android 17) were checked for discovery, the MJPEG stream, tap, swipe, long press, text input and the hierarchy.
* **Multi-touch, rotation buttons and multiple displays** are not implemented.
